# Codex 桌面主会话接管设计

日期：2026-11-02（Asia/Shanghai）

状态：已按用户授权实施并通过 workflow 验收；执行与限制见同目录实施记录及 `05-verification/CCB-MIGRATION-001/summary.md`。实际桌面重启和角色热加载不在本轮已验证结论内。

## 1. 目标与推荐方案

用户继续在 `E:\moxton-ccb` 的一个 Codex 桌面主会话中讨论需求和计划，由主会话派遣开发与 QA 子代理，检查结果并保存任务进度。三个业务仓库及现有任务编号保持不变。

推荐采用 Codex 原生子代理作为唯一主执行入口。现有 Markdown 任务、API 契约和验收记录继续使用；旧 WezTerm、MCP route 和 JSON 锁编排保留作历史参考，不同时推进新任务。

备选方案是修改旧控制器以支持无 pane 模式，能保留旧运行体系，但需要继续维护 watcher、回传、通知和状态一致性；当前优先满足单主会话派遣需求，暂不选择此方案。Vibe Kanban 等外部平台暂不引入。

成功标准：在主会话完成一次需求确认、任务落地、开发派遣、独立 QA、结果汇总和状态保存；重新开启会话后，能从文件准确恢复到下一步。

## 2. 设计依据与运行边界

- OpenAI 官方文档说明：Codex 桌面会话可以派遣子代理，适用项目指令也可以要求委派。
- 自定义角色通过项目 `.codex/config.toml` 中的 `[agents.<角色>]` 显式声明 description 和 config_file，角色文件提供 developer_instructions。实现不覆盖用户模型、权限和全局配置；具体识别以本机客户端解析验证为准。
- `AGENTS.md` 按项目目录发现指令。文档中心与业务仓库是不同 Git 根，派遣消息须明确指定任务、业务仓规则和 API 文档，不能假设文档中心规则自动覆盖三个仓库。
- 自定义角色不创建独立安全沙箱，也不自动隔离代码。权限和文件写入范围必须结合当前会话实际能力验证。
- 第一版以主会话正在执行的一轮工作为边界。退出或关闭会话后的无人值守自动续派，不作为本次承诺。

官方参考：

- https://learn.chatgpt.com/docs/agent-configuration/subagents
- https://learn.chatgpt.com/docs/agent-configuration/agents-md

## 5. 任务和通信协议

### 单一任务记录

每个任务的 Markdown 是正式主记录，至少记录 ID、业务仓、前置依赖、范围、验收、基线提交、工作区、当前 attempt、状态、开发结果和 QA 结果。`STATUS.md` 只是摘要。

新流程由主会话唯一写入正式任务状态。开发与 QA 子代理返回结果和证据，不能自行归档或改其他任务状态。旧 `TASK-LOCKS.json`、route inbox 和 watcher 不再作为新任务的状态源。

建议状态：`planned -> ready -> in_progress -> waiting_qa -> qa -> qa_passed -> completed`。阻塞单独标 `blocked` 并记录原因、已尝试动作和恢复入口；重试生成新 attempt，保留原结果。

### 每次派遣的最小输入

任务文件绝对路径、任务 ID 和 attempt、角色、业务仓或 worktree 的绝对路径、基线提交、已存在的修改、允许改动范围、依赖/API 文档、要求的验证和证据位置。

子代理执行前检查实际 Git 根与目标是否一致，不在共享工作区中执行影响其他任务的分支切换、清理或批量暂存。

### 子代理回报

返回任务 ID、attempt、目标仓库、变更文件、执行命令及退出码、验证结论、证据路径、未解决问题和建议下一步。主会话核对后推进任务，不仅凭 success 字样判定完成。

不再要求原生子代理发送 MCP ACK、固定心跳或用 WezTerm 唤醒父会话。使用当前原生派遣、追加指令、等待和回报能力；子代理不得为本次子任务创建用户侧独立聊天。

## 6. 并发、权限和 QA

- 每个业务仓库默认最多一个开发写入者；不同仓库无依赖时可并行，依赖未满足时按顺序派遣。
- 同一仓库确需并行开发时，先准备独立 worktree 和明确合并顺序。多个子代理不等于多个隔离工作区。
- 创建 worktree 前先保存当前未提交和未跟踪成果；新 worktree 不自动包含这些成果，不从旧 HEAD 验收最新本地功能。
- 当前任务不使用的其他业务仓仅提供必要读取，不由子代理自行扩大改动范围。可访问路径和权限以桌面客户端实际验证为准。
- QA 使用新子代理上下文，验收开发产生的准确工作区和差异；首次失败时记录环境、代码或证据问题，不自动回退重做全部任务。
- 保留现有契约、失败路径、UI/console/network 等适用检查。已有 `validate-qa-evidence.ps1` 先检查可复用性，再以 PowerShell 7 调用。
- QA 角色的只读要求是工作约定；测试可产生受控构建/证据文件，不能把角色说明当作独立只读安全沙箱。
- `qa_passed` 表示证据通过、等待复审。`completed` 需要父会话完成结果核对、文档同步并说明提交/集成情况；上线状态另记，不与任务完成混淆。
- 不默认沿用旧 repo-committer 的自动 push 行为。提交、推送和部署分别记录，不将归档等同于发布。

## 7. 工作区与历史系统处理

第一步生成分类清单，记录文档中心和三个业务仓的原有修改。正式任务/API 文档、公开产品资料、验收摘要应审阅后纳入版本控制；客户线索表格、测试凭据、原始日志、缓存、PID 和部署二进制单独处理。

已跟踪的运行数据库与日志，需要决定保留位置后取消 Git 跟踪；增加 `.gitignore` 不会自动移除既有跟踪。采用定向改动，不执行 `git clean -fd`、`reset --hard` 或全仓批量删除。

旧系统先逻辑退役：默认入口、活动模板和规则不再调用旧 controller/monitor/notifier。确认没有相关存活进程后记录退役；不根据旧 PID 文件直接结束进程。

旧锁和日志保留快照，活动任务通过核对迁入新流程。原生派遣与旧 controller 禁止同时管理相同任务。

原有成果基线和本次迁移分别形成提交，之后每轮任务有独立交付范围。文档中心干净表示没有来源不明的改动，不要求业务运行目录为空。

## 8. 会话恢复

主会话启动时读取根规则、工作流指南、STATUS、active 任务和最新交接记录，再检查实际 Git 差异与依赖。

子代理 ID 仅作为当前执行期线索，不能代替持久任务状态。会话中断后，未确认结束的任务先标记待核实，核对实际运行、差异和产物后再续派，避免重复开发。

每轮结束在任务文件保存最后完成步骤、未完成项、下次入口和验证命令。必要时新增 `04-projects/CURRENT-ROUND.md` 作为单页交接索引，不复制完整任务正文。

| 批次 | 内容 | 通过条件 |
|------|------|----------|
| A：保全和基线 | 清点四仓修改，分类资料与运行态，明确正式资产和本地保留项 | 原有有效内容可恢复，没有被静默删除或混入迁移差异 |
| B：规则与模板 | 根规则、角色、工作流、模板和三个业务仓协议对齐 | 活动规则没有 Claude 主指挥限制或强制旧 route 回报，角色配置可解析 |
| C：最小派遣验证 | 先进行只读子代理检查，再在明确基线上执行一个小改动任务并独立 QA | 主会话收到实际变更、命令、证据和 QA 结论；旧 watcher 未参与状态推进 |
| D：恢复与整理 | 用新会话核对任务进度，更新 README、STATUS 和历史入口 | 无需重讲项目背景即可确定下一步；正式资产已纳管，Git 状态与交付说明一致 |

还需验证：不满足依赖时不派遣；QA 失败不会归档；重复/旧 attempt 回报不会覆盖当前结果；非任务文件没有意外改动；没有发生未授权 push、部署或真实数据操作。
